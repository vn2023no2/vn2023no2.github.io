1. Reliability & SLO/SLI/SLA

▼
Bạn định nghĩa SLI, SLO, SLA như thế nào? Cho ví dụ thực tế? ▶
Concept

SLI (Service Level Indicator) là chỉ số đo lường thực tế, ví dụ: tỷ lệ request thành công trong 5 phút.

SLO (Service Level Objective) là mục tiêu nội bộ, ví dụ: SLI ≥ 99.9% trong 30 ngày.

SLA (Service Level Agreement) là cam kết pháp lý với khách hàng, thường thấp hơn SLO ~10-20% để có buffer.

Ví dụ thực tế: Với API thanh toán: SLI = % request < 300ms, SLO = 99.5%, SLA với đối tác = 99%.

Khi error budget cạn kiệt, bạn xử lý như thế nào với product team? ▶
Process

Khi error budget hết, tôi đề xuất feature freeze tạm thời và ưu tiên hoàn toàn cho reliability work. Cụ thể:

  • Trình bày dashboard error budget cho leadership để alignment.
  • Yêu cầu team product dừng deploy tính năng mới cho đến khi budget phục hồi.
  • Tập trung vào giảm toxi latency, fix lỗi recurring, cải thiện runbook.
Bạn đã từng thiết kế hệ thống high availability chưa? Kiến trúc như thế nào? ▶
Architecture

Kiến trúc HA điển hình tôi đã triển khai trên AWS:

  • Multi-AZ deployment với ALB phân tải giữa các AZ.
  • EKS cluster với node groups trải rộng ≥ 3 AZ.
  • RDS Multi-AZ với read replica cho read-heavy workload.
  • Sử dụng circuit breaker pattern để tránh cascade failure.
  • Health check + auto-healing qua Kubernetes liveness/readiness probe.

2. Incident Response & Post-mortem

▼
Quy trình xử lý incident lúc 3 giờ sáng khi hệ thống production down? ▶
Process
  1. Acknowledge alert ngay, thông báo channel incident.
  2. Assess severity: bao nhiêu user bị ảnh hưởng? Revenue impact?
  3. Mitigate trước, investigate sau: rollback nếu deploy gần đây, scale up nếu resource thiếu.
  4. Loop in người cần thiết (on-call manager nếu SEV1).
  5. Document live trên incident channel mọi hành động đã làm.
  6. Sau khi ổn định: viết post-mortem trong 48h.
Bạn viết post-mortem như thế nào? Ai chịu trách nhiệm? ▶
Process

Post-mortem phải blameless — tập trung vào hệ thống, không chỉ trích cá nhân. Cấu trúc gồm:

  • Timeline sự kiện chi tiết.
  • Root cause (5-whys hoặc fishbone diagram).
  • Impact: thời gian, số user, doanh thu ảnh hưởng.
  • Action items có owner và deadline cụ thể.

Người on-call chịu trách nhiệm viết draft, team review và approve.

3. Kubernetes & Docker

▼
Bạn troubleshoot một pod liên tục CrashLoopBackOff như thế nào? ▶
Troubleshooting 
kubectl describe pod <pod-name>   # xem Events
kubectl logs <pod-name> --previous # xem log lần crash trước
kubectl exec -it <pod-name> -- sh  # nếu pod còn sống

Nguyên nhân thường gặp: OOMKilled, liveness probe fail, missing config/secret, image lỗi, port conflict.

Chiến lược deploy zero-downtime của bạn là gì? ▶
Deployment
  • Rolling update: mặc định K8s, thay thế pod dần dần.
  • Blue-Green: chạy song song 2 env, switch traffic khi ready — rollback nhanh nhất.
  • Canary: route 5-10% traffic vào version mới, monitor rồi tăng dần — an toàn nhất cho fintech.

Tôi ưu tiên canary deploy cho các service thanh toán vì rủi ro cao.

4. Cloud – AWS

▼
Bạn thiết kế multi-AZ architecture cho fintech app như thế nào? ▶
Architecture
  • VPC với public/private subnet trải 3 AZ.
  • ALB → EKS (node group mỗi AZ) → RDS Multi-AZ.
  • ElastiCache (Redis cluster mode) cho session, rate limiting.
  • S3 + CloudFront cho static assets.
  • Route 53 health check + failover routing.
Bạn tối ưu chi phí cloud như thế nào trong môi trường production? ▶
Cost Optimization
  • Dùng Spot Instances cho workload không critical (batch, non-prod).
  • Right-size EC2/RDS dựa trên CloudWatch metrics thực tế.
  • Reserved Instances / Savings Plans cho baseline workload.
  • Xóa unused EBS, snapshot, ELB, Elastic IP.
  • Dùng AWS Cost Explorer + budget alert để detect anomaly.

5. Monitoring & Observability

▼
Sự khác biệt giữa monitoring và observability? ▶
Concept

Monitoring trả lời: "Hệ thống có đang hoạt động không?" — dựa trên metrics và alert đã được định nghĩa trước.

Observability trả lời: "Tại sao hệ thống lại hoạt động như vậy?" — bao gồm logs, metrics, traces để debug unknown unknowns.

3 pillars: Metrics (Prometheus), Logs (ELK), Traces (Jaeger/OpenTelemetry).

Bạn thiết lập alerting như thế nào để tránh alert fatigue? ▶
Best Practice
  • Chỉ alert khi user bị ảnh hưởng thực sự (symptom-based), không alert từng nguyên nhân nhỏ.
  • Phân loại severity rõ ràng: P1 (wake up), P2 (business hours), P3 (ticket).
  • Dùng AlertManager inhibition + silencing để tránh alert cascade.
  • Review và tắt alert không actionable hàng tháng.

7. Security & Compliance (Fintech)

▼
Bạn đảm bảo secrets management trong K8s như thế nào? ▶
Security
  • Không lưu secret dạng plaintext trong code hay ConfigMap.
  • Dùng AWS Secrets Manager + External Secrets Operator để inject vào pod.
  • Hoặc HashiCorp Vault với Vault Agent Sidecar.
  • Enable encryption at rest cho etcd (K8s secret encryption).
  • Rotate secret định kỳ, audit access log.
Kinh nghiệm với network policy và RBAC trong Kubernetes? ▶
Security
  • Network Policy: áp dụng default-deny, chỉ allow traffic cần thiết giữa namespace/service.
  • RBAC: principle of least privilege — mỗi service account chỉ có quyền tối thiểu cần thiết.
  • Audit RBAC định kỳ, dùng kubectl auth can-i để verify.
  • Dùng OPA/Gatekeeper để enforce policy tự động.

8. Câu hỏi hành vi (Behavioral)

▼
Khi deadline gấp nhưng hệ thống chưa đủ ổn định để release, bạn làm gì? ▶
Behavioral

Tôi sẽ định lượng rủi ro cụ thể rồi trình bày cho stakeholder, không chỉ nói "chưa sẵn sàng". Ví dụ: "Deploy lúc này có 30% khả năng gây downtime 15 phút, ảnh hưởng X user." Sau đó đề xuất các option:

  • Delay thêm N ngày để fix issue cụ thể.
  • Release với feature flag, chỉ enable cho % nhỏ user trước.
  • Deploy với rollback plan rõ ràng và người trực sẵn sàng.
Bạn bất đồng với quyết định kỹ thuật của team, bạn xử lý thế nào? ▶
Behavioral

Tôi theo nguyên tắc "Disagree and commit". Trước tiên nêu quan điểm với data/reasoning rõ ràng. Nếu team vẫn đi theo hướng khác sau khi đã nghe, tôi commit và hỗ trợ hết mình. Đồng thời ghi lại concerns để review lại sau nếu issue xảy ra.

Bạn onboard và mentor junior SRE như thế nào? ▶
Leadership
  • Tuần 1: shadow on-call, đọc runbook, hiểu hệ thống tổng thể.
  • Tuần 2-4: tự handle P3 incident với support.
  • Tháng 2: own một small reliability project.
  • 1-on-1 hàng tuần để unblock và feedback.
